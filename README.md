The Second Day is a health-synthesis newsletter about infection-associated chronic illness, including definitions, proposed mechanisms, and care evidence. Its canonical issue data and Markdown, paste-ready HTML, and feed renderings stay in `content/issues/`. The cited scientific corpus is shared with [the health curriculum](../health-education-curriculum-services-section/README.md) and the [medical-science material](../../../../../../../../../science-services-section/services/natural-science-services-section/services/biological-science-services-section/services/medical-science-services-section).

Draft delivery has two **different original providers**: [Red Cup newsletter issue engineering](https://github.com/red-cup-engineering/email-newsletter-engineering-services-section) validates and composes the three carriers; [Red Cup Buttondown engineering](https://github.com/red-cup-engineering/buttondown-engineering-services-section/blob/main/scripts/publish-issue-draft.mjs) owns the `publish-newsletter-draft` effect. The newsletter composer does **not** contain a `publish-issue-draft.mjs` script. The old command and `BUTTONDOWN_API_KEY` convention here were not executable contracts.

For a separately authorized **draft only**, the real Buttondown publisher's installed operator context must select the original issue directory and private data root, a **verified public issue URL**, the actual Buttondown newsletter routing name and its scoped key. Its source-owned CLI contract is:

```sh
publish-newsletter-draft <issue-dir> --newsletter <verified-newsletter-handle> --feed-link <verified-public-issue-url> --status draft --data-root <private-publication-data-dir>
```

The Buttondown provider resolves its newsletter-specific key through `CREDENTIALS_DIRECTORY/buttondown/<newsletter>.api-key` using the existing credential-custody service; **do not** set a process-wide `BUTTONDOWN_API_KEY`, place a key in Git, or invent the newsletter handle from the archive hostname. Its operation recomposes reviewed files, creates a private draft, and records the provider-returned identifier under the explicitly selected private publication data directory. Require qualified source/editable-artifact receiving, independent scientific/accessibility review and observed public hosting first. If submission is ambiguous, reconcile with the original provider before any retry; an attempted draft is not a returned draft ID. Sending subscribers, scheduled publication and manual cross-posting to emsenn's *Letters to the Web* require separate approval. Existing historical journal records remain under their original owner.

The archive name is `secondday.561.group`; this document does not establish that the archive is deployed. ### Issue 004: Encounter requirements and source/receiver oracle (28 October 2026)

- **CH-004-AIR-01 · P0, safety.** The room operator SHALL refuse ozone-generating air cleaners in an occupied space. Positive case: appropriately sized filtration maintained and observed operating; refusal case: an ozone generator advertised as an air purifier. [US EPA's respiratory-virus guidance](https://www.epa.gov/indoor-air-quality-iaq/air-cleaners-hvac-filters-and-respiratory-viruses) expressly rejects ozone generators in occupied spaces. Check the canonical checklist *and* actual reader artifact. This does not certify an individual installation.
- **CH-004-ACCESS-02 · P0, situated participation.** The operator SHALL ask which languages and communication modes participants can use, without requiring diagnosis or presuming English, and arrange feasible formats/interpretation or change the meeting format. Positive case: a request for interpretation or low-bandwidth written participation leads to a genuinely usable alternative; refusal case: an English-only visual checklist treated as universally accessible because its HTML has `lang="en"`. W3C [WCAG 2.2, 3.1.1](https://www.w3.org/WAI/WCAG22/Understanding/language-of-page.html) requires identifying the language *actually used in that page*; it does not establish any recipient's preference. Independently test the actual participant-specific alternative before claiming accessibility.
- **CH-004-LINK-03 · P0, source/derivative integrity.** Keep both canonical issue references and each of three composed Markdown, paste-HTML and feed previews pinned to the *same* immutable source commit for the checklist. Refuse the former obsolete checklist pin. The linked Git revision, editable Markdown and companion HTML must contain both safeguards; the 15 task controls, five navigation targets, named landmarks and print marks must not regress. Source parity is **not** installed composer execution, medical/editorial review, assistive-technology acceptance, public hosting or sending. The original Red Cup composer, local public-health editor, independent accessibility reviewer and eventual publisher remain separate receivers.
